## 2. 日志时区修复

### 2.1 根因

当前 `AppLogger` 直接使用未配置时区的 `ISO8601DateFormatter`。格式化器默认输出 UTC，因此日志时间以 `Z` 结尾，与用户 macOS 当前的 `+08:00` 不一致。

### 2.2 设计

- 保留 ISO 8601 日志格式，避免使用随语言和地区变化的日期字符串。
- 日志格式化器使用 `TimeZone.autoupdatingCurrent`，在系统时区变化后自动跟随。
- 新日志包含明确的数字时区偏移，例如 `2026-08-18T13:36:22+08:00`。
- 只影响新写入的应用日志；不改写历史日志。
- 不改变配置 JSON 的日期编码，也不改变 Mihomo 自身输出的日志格式。

### 2.3 验证

抽离一个可独立测试的日志时间格式化单元。测试使用固定日期和固定 `+08:00` 时区，验证结果包含正确的本地时间和偏移，避免测试依赖执行机器的实际时区。

## 3. 主窗口单实例修复

### 3.1 根因

主界面当前使用 SwiftUI `WindowGroup`。菜单栏每次调用 `openWindow(id: "main")` 时，系统允许为同一场景继续创建窗口，因此会出现多个管理窗口。

### 3.2 方案比较

1. **单例 `Window` 场景（采用）**：将主场景改为 macOS 13 支持的 `Window`。已打开时复用并置前，关闭后允许重新创建，系统层面保证最多一个实例。
2. 自建 `NSWindowController`：显式保存窗口引用，控制能力更强，但需要额外处理 SwiftUI 内容、释放和应用激活生命周期。
3. 点击时扫描窗口：检测到现有窗口就激活，否则调用 `openWindow`。实现简单，但连续调用存在检查与创建之间的竞态，不能从结构上保证唯一性。

MVP 采用方案 1，保持原有界面、窗口尺寸、关闭后隐藏 Dock 图标和后台常驻行为不变。

### 3.3 打开行为

- 主窗口已存在：菜单栏命令只激活应用并将该窗口置前。
- 主窗口已关闭：重新打开一个主窗口，并恢复 Dock 图标。
- 主窗口最小化：恢复并置前，不创建新窗口。
- 连续多次点击：始终最多存在一个普通管理窗口。
- 关闭管理窗口：应用和菜单栏继续运行，Dock 图标消失。

### 3.4 验证

增加一个不依赖真实用户点击的窗口场景结构测试，确认应用声明使用单例 `Window` 而不是 `WindowGroup`；同时保留现有菜单栏图标测试。构建后进行一次人工验收：反复打开、最小化、关闭再打开，检查窗口数量和 Dock 状态。

## 4. README 设计

README 使用自然、简洁的中文，不写产品宣传式内容，核心信息包括：

- Surge 本身不支持 SSR，本工具通过 Mihomo 把 SSR 节点转换为 Surge 可用的本地 SOCKS5 节点。
- 系统要求、最短使用步骤、本机构建方法和数据目录。
- 明确工具不会自动修改 Surge 配置。
- 用一小节列出 MVP 当前限制。
- 指向完整方案设计与开发交接文档，避免把 README 写成内部设计说明。
